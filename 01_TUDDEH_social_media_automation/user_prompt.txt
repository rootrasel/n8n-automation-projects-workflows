4A. Automation Pause Controls
Phase 1 must include a global three-state automation control in an n8n Data Table. This is technical/operational state and must not create another Google Sheets tab.
Global Automation Mode
Store one centrally managed value in n8n Data Tables: AUTOMATION_MODE = ACTIVE | PAUSED | MAINTENANCE.
ACTIVE: all Phase 1 workflows operate normally.
PAUSED: block NEW content-production intake, but allow work already past the intake gate to finish. WF-13A Scheduling Verification, WF-13B Published Verification, WF-15 Daily Ready-to-Schedule Digest, WF-98 Reconciliation, WF-99 Error Handling, and WF-00 business-folder provisioning may continue.
MAINTENANCE: block new content production and pause non-essential operational workflows while system changes are being made. WF-98 reconciliation and WF-99 error handling remain available as integrity/safety workflows. Do not start new OpenAI/FFmpeg generation while in MAINTENANCE.
Single Intake-Gate Rule
Check AUTOMATION_MODE once at WF-01 intake, before internal job registration, locking, or any paid OpenAI/FFmpeg work. Do not add pause checks to every downstream node.
If PAUSED or MAINTENANCE is activated after a job has already passed the WF-01 intake gate, that in-flight job runs to completion. Do not attempt to interrupt an active OpenAI request, FFmpeg render, Drive save, or approval-package step mid-execution. Rule: finish what has started; block what has not started.
Per-Business Pause
The Businesses tab includes a separate human-facing field named Automation Status with values Active | Paused. This field is distinct from the existing business Status field.
Business Status represents whether the business is an eligible/live business record. Automation Status represents whether NEW social-content jobs may begin for that business.
At WF-01 intake, after the global AUTOMATION_MODE check and before job registration, check the business's Automation Status. If Automation Status = Paused, gracefully skip the job: do not register/lock it, do not call OpenAI, and do not treat the pause as an error.
If a business is paused after one of its jobs has already passed WF-01 intake, that in-flight job completes normally. Previously approved, Ready-to-Schedule, Scheduled, Published, Performance, and Drive records remain untouched.
WF-02 retains the existing validation that the Business exists and Business Status is Active. Automation Status = Paused is NOT a WF-02 validation failure; it is a separate WF-01 intake gate.

7A. WF-00 — Business Folder Provisioning
Purpose: automatically create the standardized per-business Google Drive asset structure when a business is added to the automation. The seven master folders and the two Approved Content subfolders already exist and must NOT be recreated by this workflow.
Trigger
Run when a business becomes active/eligible for the social-media automation and its existing Businesses-tab Business Drive Folder field is blank or no valid mapped Drive folder ID exists in the n8n Data Table.
Required logic
1. Read the business record from the Businesses tab.
2. Check the n8n Data Table for an existing durable Google Drive business-folder ID.
3. If a valid mapped folder already exists, do not create another folder. Reuse it and ensure the human-usable folder URL is present in the Businesses tab.
4. If no mapped folder exists, check under 01 Business Assets for an existing folder already associated with that business before creating anything.
5. If none exists, create one parent folder named for the business under 01 Business Assets.
6. Inside that parent folder, create exactly: 01 Brand, 02 Photos, 03 Videos, 04 Reference, and 05 Archive.
7. Verify that the parent folder and all five required subfolders exist.
8. Store the parent business-folder ID and required subfolder IDs in the n8n Data Table.
9. Write the human-usable parent Business Drive Folder URL to the existing Businesses-tab field.
10. Mark the internal provisioning state complete only after verification succeeds.
Safeguards
• Use Google Drive folder IDs as durable internal identifiers. Do not use the business name as the primary identity after provisioning.
• The workflow must be idempotent: retries, duplicate triggers, or reactivation of a business must not create duplicate folders.
• A later business-name change must not cause n8n to create a second folder. Continue using the stored Drive folder ID; renaming the folder can be handled separately if desired.
• If only some subfolders exist, create only the missing required subfolders and then verify the complete structure.
• If provisioning partially fails, do not treat the business as ready for content generation. Retry temporary failures through WF-99 or alert TUDDEH when human action is required.
• WF-00 must never create or modify the seven master folders because those are already provisioned.
8. WF-01 — Marketing Queue Trigger
1. Poll the Marketing Queue on a short interval (for example every 10 minutes).
2. For each candidate row, check global AUTOMATION_MODE. If PAUSED or MAINTENANCE, do not start a new production job.
3. If global mode permits production, resolve the Business record and check Automation Status. If Paused, skip the row gracefully without creating an internal job/lock.
4. Only when global mode permits production AND business Automation Status = Active, select rows where Production Status = Planned and no internal job lock already exists.
5. Create/reuse one internal n8n job ID for that Sheet row, store the Sheet-row mapping, and create the idempotency/processing lock.
6. Change Production Status to Generating only after job registration succeeds, then pass the job to WF-02.

15. WF-10 / WF-11 — Approval and Revision
Send the approval request by Gmail with preview, caption, tags, CTA and actions: Approve, Request Revision, Reject.
Each approval action carries the internal job ID, current approval version and a unique token.
A stale approval link must never approve a newer revision.
Request Revision: write human revision notes to Revision Notes, set Production Status = Revision Needed, create a new version, then return to Ready for Review.
Approve: verify current version, then set Production Status = Approved and call WF-12.

18. WF-13A — Schedule Requested → Scheduled
1. Human schedules the post using Meta Business Suite, TikTok/native tools, or another approved manual scheduler.
2. Human enters Scheduled Date / Time and changes Scheduling Status to Schedule Requested.
3. n8n verifies the internal job is currently Ready to Schedule and is not already Scheduled or Published.
4. Move the approved package from 01 Ready to Schedule to 02 Scheduled.
5. Verify the destination package exists and the source is no longer the active Ready-to-Schedule package.
6. Only after verification, change Scheduling Status to Scheduled.
7. Update operational status/date inside POSTING_INFO.txt if desired.
If the Drive move fails, leave Scheduling Status = Schedule Requested, log the error in n8n, and alert TUDDEH. Never falsely mark it Scheduled.
19. WF-13B — Publish Confirmed → Published
1. After the post is live, human pastes the Published URL and changes Scheduling Status to Publish Confirmed.
2. n8n verifies the internal job is currently Scheduled and has a Published URL.
3. Move the package to 06 Published Content/[YYYY-MM]/[Business].
4. Verify the move.
5. Only after verification, set Scheduling Status = Published.
6. Update operational metadata.
7. Create one Performance row for EACH platform on which the content was published.
8. Automatically populate each Performance row with Business, Content Focus, Selected Listing, Content Format, Platform, and Publish Date.
9. If the same content was published to Instagram and Facebook, create two separate Performance rows (one Instagram row and one Facebook row). Never combine platform metrics into one multi-platform row.
10. Reach, Engagements, Link Clicks, Goal Achieved, and AI Learning remain performance-stage fields. In Phase 1, performance metrics may be entered manually.
If the move fails, leave Scheduling Status = Publish Confirmed, log the error, and alert TUDDEH.

WF-98 must compare, for every active internal job:

2. n8n Data Table state: internal job ID, internal lifecycle state, approval version, processed/idempotency lock, and expected Drive location.
